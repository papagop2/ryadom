# Развёртывание «Рядом» на ПК №2

## Факт и целевое состояние

Сейчас `LocalAppServer` на `http://192.168.50.150:8080/` обслуживает прежнюю тестовую страницу. Проект «Рядом» лежит на этом же ПК №2: `C:\Users\User\Desktop\netral2\superapp-pc2`, собранная статика — в `C:\Users\User\Desktop\netral2\superapp-pc2\dist`. Проверка через временный loopback preview проходила; отдельный сайт IIS ещё не создан, PostgreSQL ещё не установлен, постоянная служба API не настроена. Не заменять старый сайт. Работа идёт локально, без SSH. В истории проекта пароль RDP не хранить.

## Сборка на ПК №2

1. Зависимости уже лежат в `node_modules` (перенесены готовыми, включая `pg`), потому что реестр npm с ПК №2 отвечает `ECONNRESET`. Ставить `npm ci` на этом ПК не нужно и без сети он не пройдёт; при добавлении пакетов переносить их с ПК №1 вместе с `package-lock.json` и не отключать проверку TLS или целостности. Резервный путь — офлайн-кэш в `C:\Users\User\Desktop\netral2\npm-cache`, если он будет заполнен для текущего lock-файла.
2. Из `C:\Users\User\Desktop\netral2\superapp-pc2` выполнить `npm.cmd run build`, `npm.cmd test`, `node tests/smoke.mjs`. Последняя команда занимает loopback-порты `3100` и `4173` только на время проверки, запускать до установки постоянной службы на `3100`.
3. Миграции и демоданные: `npm.cmd run migrate`, `npm.cmd run seed` (порядок и переменные окружения — в `STATUS.md`). Роли и базу создаёт `deploy/db-setup.sql` от суперпользователя; пароли передаются переменными psql и не попадают в репозиторий. Роль `rjadom_migrator` владеет схемой, `rjadom_app` получает только `select/insert/update/delete` и не может менять схему.

Цель: мобильный клиент открывает отдельный сайт по HTTPS; IIS отдаёт `dist/` и проксирует `/api/*` в Node на `127.0.0.1:3100`. WinSW запускает Node без входа пользователя; PostgreSQL слушает только `127.0.0.1:5432`. Статика, логи, конфигурация и секреты раздельны. ПК №2 со старой Windows доступен только из доверенной LAN и предназначен для демоданных.

## Контрольный список этапа 0

1. Выбрать имя HTTPS и способ доверия: локальный DNS + свой CA на тестовых устройствах, либо свой домен с публичным сертификатом через DNS-подтверждение. Проверить разрешение имени с телефона. Не отключать проверку сертификата и не копировать приватный ключ CA на сервер.
2. Снять резервную копию IIS. Установить подходящие версии URL Rewrite и ARR, настроить отдельный сайт, проксирование `/api/*` и правило LAN только для HTTPS. Старый сайт и регламент удалённого доступа сохранить. Не включать SPA-fallback для API, отсутствующих статических файлов и файлов service worker.
3. Установить актуальный патч Node LTS и PostgreSQL, проверить исполнение под отдельной Windows-учёткой без административных прав. Установить API как службу WinSW, отдельной ролью применить миграции. Пароли хранить вне корня IIS с ограниченными ACL.
4. Опубликовать артефакт, собранный на ПК №2, из отдельной директории релиза. Проверить `/api/health/live`, затем `/api/health/ready` и тестовую БД. `503 database_not_configured` в текущем каркасе ожидаем и означает, что готовность полного стека не подтверждена.
5. Проверить Android/iOS, доверие к HTTPS, установку, офлайн-экран, отсутствие доступа к API и БД напрямую с телефона. Проверить после штатной перезагрузки и восстановить бэкап в отдельную БД. Не перезагружать ПК в середине пользовательской работы.
